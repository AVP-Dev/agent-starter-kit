## 4. Жёсткие правила (Zero Tolerance — нарушать нельзя)

### 4.1. Архитектура: «Skeleton + Pluggable Modules»
1. **Skeleton (Каркас):** Проектируется Человеком-Архитектором.
   - Единая точка валидации входных данных (Zod / Pydantic).
   - Единая схема данных (SSOT) и контекст сессии/пользователя.
   - Шина событий/очередей и централизованная обработка ошибок.
2. **Pluggable Modules (Сменные модули):** Наполняются ИИ-агентом.
   - Каждый модуль замкнут в границах своего типизированного контракта.
   - **Запрет скрытого сцепления:** Модуль НЕ имеет прямого доступа к чужим приватным таблицам БД или чужому состоянию.
   - **Принцип заменяемости (Disposable Modules):** При изменении требований модуль перегенерируется с нуля по обновленному контракту, а не затягивается в недели спагетти-рефакторинга.

### 4.2. Матрица делегирования ответственности (Delegation Matrix)
Любая задача разделяется строго по уровню ответственности:

| Уровень задачи | Ответственный | Скоуп |
|---|---|---|
| **Зона 1: Полное делегирование (100% AI)** | ИИ-агент автономно | Чистые функции без сайд-эффектов, DTO-конвертеры, утилиты, верстка UI-компонентов по дизайн-системе, парсеры данных, юнит-тесты краевых условий |
| **Зона 2: Контрактное делегирование (50 / 50)** | Человек согласует контракт → ИИ реализует | CRUD-эндпоинты, обработчики очередей задач, интеграции внешних API, Server Actions, генерация отчетов. Агент не пишет код до фиксации сценариев сбоев (Failure Modes) |
| **Зона 3: Нулевое делегирование (0% AI / Только человек)** | Архитектор (ручной контроль) | Модель владения данными и схема БД, финансовые транзакции, модель прав (RBAC/ABAC), архитектура безопасности. Запрещено модифицировать агенту без Confirmation Gate |

### 4.3. Предпроектный DESIGN-манифест (Zero Vibe Coding)
Перед написанием кода для любой нетривиальной задачи (новый API-эндпоинт, фоновый воркер, интеграция, модель данных или модуль) агент **ОБЯЗАН** зафиксировать краткий манифест (см. [docs/design-manifest-template.md](docs/design-manifest-template.md)):
1. **Инварианты системы (Invariants):** Что *НЕ МОЖЕТ* произойти ни при каких обстоятельствах.
2. **Конечный автомат (State Machine):** Четкие состояния сущности (`Draft → Pending → Completed / Failed`) и допустимые переходы.
3. **Границы сбоев (Failure Modes & Idempotency):**
   - Поведение при сетевых таймаутах и отказах внешних сервисов (fail-closed vs fallback).
   - Защита от дублирующих запросов и повторных вебхуков (ключи идемпотентности).
4. **Критерии доказательства качества (Acceptance Invariants):** Список конкретных негативных сценариев и стресс-проверок.

### 4.4. Качество кода и обработка ошибок
1. **Абсолютный запрет `any`:** Все типы строго описываются интерфейсами или схемами валидации.
2. **Абсолютный запрет глушения ошибок:**
   - ❌ Запрещено: пустые блоки `catch {}`, `catch (e: any)`, `.catch(console.error)`.
   - ✅ Обязательно: типизация `catch (error: unknown)`, явное извлечение сообщения и проброс/логирование контекста.
3. **Fail-Closed валидация на границах:** Все данные из внешнего мира валидируются схемами ДО передачи в бизнес-логику.
4. **Non-Destructive Data Policy:** Категорически запрещено решать проблемы рендеринга или трансформации удалением данных (`DROP`, `TRUNCATE`, сброс таблиц). Ошибки чинятся в логике резолверов и обратимыми миграциями.
5. **Запрет блокирующих вызовов в UI:** Никаких синхронных `confirm()` или `alert()`, ломающих мобильные браузеры (iOS Safari).

### 4.5. Стандарт интерфейса, дизайн-токенов и визуальных тем (Theme-Driven Visual Architecture)
1. **Инвариант «Zero Hardcoded Colors in Components»:**
   - Категорически запрещено зашивать в верстку компонентов сырые hex-коды (`#1e293b`), arbitrary values или жестко зашитые классы базовых палитр (напр. `bg-zinc-900`, `text-blue-500`).
   - Вся стилизация строится **исключительно на семантических дизайн-токенах / CSS-переменных**:
     `--background`, `--foreground`, `--primary`, `--primary-foreground`, `--muted`, `--muted-foreground`, `--accent`, `--accent-foreground`, `--border`, `--input`, `--ring`, `--radius`.
   - Любая тема (светлая, тёмная, корпоративная, нео-брутализм, скандинавская, киберпанк и др.) объявляется как изолированный набор значений токенов (`:root`, `.dark`, `[data-theme="..."]`).
   - Добавление, замена или переключение темы оформления в проекте обязаны производиться **без модификации кода компонентов** (Zero Component Edits).
2. **Иерархия действий и типографика (Anti-AI-Slop):**
   - На одном экране/вьюпорте допускается не более одного действия первого порядка (Primary CTA). Второстепенные действия оформляются строго как Secondary, Outline или Ghost.
   - Запрещены однообразные плоские карточки с размытыми тенями без четких границ и контраста.
   - Типографическая шкала строго фиксирована через токены проекта (например, `text-xs` .. `text-3xl`, tracking, line-height).
3. **Состояния элементов и интерактивность:**
   - Каждый интерактивный элемент обязан иметь явно описанные состояния: `:hover`, `:active`, `:focus-visible` (доступный фокусный контур для клавиатурной навигации), `:disabled` и состояние загрузки (`loading state / skeleton`).
4. **Семантика и доступность (Fail-Closed a11y):**
   - Запрет кликабельных `<div>` или `<span>` со слушателями клика — строго нативные `<button>`, `<a>`, `<input>` с доступными `aria-label` при отсутствии явного текста.
   - Минимальный коэффициент контрастности текста к фону: не менее 4.5:1 (WCAG AA).
   - Мобильная адаптивность (Mobile-First): верстка гарантированно не ломается и не имеет горизонтального скролла в диапазоне от 360px до 4K.

## 5. Автоматическая верификация (Automated Verification Gate)

Чтобы вайб-кодинг был устойчивым и автоматизированным, агент **НЕ СЧИТАЕТ задачу завершенной**, пока не пройден гейт автоматической проверки:

1. **Обязательный запуск команд верификации:**
   - **TypeScript / JavaScript:**
     ```bash
     pnpm typecheck   # либо: npx tsc --noEmit
     pnpm lint        # проверка линтером (ESLint / Biome)
     pnpm test        # прогон автотестов
     ```
   - **Python:**
     ```bash
     ruff check .     # линтинг и форматирование
     mypy .           # строгая проверка типов
     pytest           # прогон автотестов
     ```
   - **Go:**
     ```bash
     go vet ./...
     golangci-lint run
     go test -v ./...
     ```
2. **Green-Bar Requirement:** Любая ошибка линтера, типов или тестов должна быть устранена до передачи ответа пользователю.
3. **Обязательное покрытие тестами каждой итерации:**
   - Любая новая функция/эндпоинт сопровождается юнит- или интеграционным тестом.
   - Тестируется не только Happy Path, но и минимум 1-2 краевых/негативных сценария (сбой сети, невалидные входные данные, дублирование ключа).

## 6. Безопасный Git / GitHub протокол и атомарные коммиты

### 6.1. Safe Remote Sync (Проверка актуальности перед началом)
Перед началом работы или крупной итерации агент обязан проверить синхронизацию с удаленным репозиторием:
```bash
git fetch origin && git status -uno
```
- ⚠️ **Правило обнаружения отставания:** Если локальная ветка отстает от удаленной (`Your branch is behind 'origin/...' by N commits`):
  - **Агент ОБЯЗАН ОСТАНОВИТЬСЯ** и уведомить пользователя.
  - **Категорически запрещен слепой `git pull`:** Автоматический pull может вызвать скрытые мерж-конфликты. Пользователь должен подтвердить синхронизацию.

### 6.2. Атомарные коммиты в конце каждой итерации
После успешного прохождения шагов (Код написан → Тесты написаны → Automated Verification Gate зеленый) агент фиксирует изменения коммитом по стандарту Conventional Commits:
```bash
git add <конкретные_файлы>
git commit -m "feat(module): добавить обработку RAG-пайплайна с pgvector"
# или fix(...), test(...), refactor(...)
```
*Запрещено коммитить битый или не прошедший тесты код.*

## 7. Confirmation Gate Protocol (Запрос подтверждения)

Если задача требует:
- изменения схемы БД или миграций;
- изменения системы авторизации или прав доступа (RBAC);
- изменения межсервисных контрактов или протоколов безопасности,
агент **ОБЯЗАН остановиться** и предоставить человеку:
1. **Root Cause Analysis:** Точная причина проблемы.
2. **Impact Matrix:** На какие компоненты и сервисы повлияет изменение.
3. **План изменений:** И дождаться явного подтверждения от пользователя ДО редактирования файлов.
